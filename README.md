Turn a single DeepSeek Harness session into a full game development studio.
**49 agents. 83 skills. One coordinated AI team.**

You describe the game; the studio asks the questions a real one would, writes the documents a real one
writes, keeps the project's memory between sessions, and plays the result in a browser to see what broke.
It is a **port of [Claude Code Game Studios](https://github.com/Donchitos/Claude-Code-Game-Studios)
(CCGS)** — the skills, agents, rules and documentation come from upstream (MIT); this repository provides
the DeepSeek Harness runtime: Node hooks, skill generation, machine-level install, and the plugin bridge.

| Port strategy | Dual stack, one source: `.claude/` is the content source (upstream text, kept verbatim); `.dsh/**` is generated by `tools/build-dsh.mjs` |

Upstream targets Claude Code (`.claude/`, `.sh` hooks, `bash` one-liners, `@path` imports). None of that
runs under DSH (no `bash` tool, piped child processes are denied by the sandbox, `@path` is not expanded),
so DSGS generates a DSH-runnable equivalent instead of editing upstream content, and proves **no content loss**.

> The plugin package bundles the framework under `payload/` — you never need to look at it while using the plugin.

## Install

### ① Web client

`Plugins` → `Add plugin` → paste `https://github.com/HYClub/deepseek-harness-game-studios` → **Install** → restart `dsh web`.

```pwsh
dsh plugin --profile web add https://github.com/HYClub/deepseek-harness-game-studios
```

### ② Desktop client

Open the desktop app, then `Plugins` → `Add plugin` → paste the same URL → **Install** → restart the app.

On first load the plugin installs the framework at machine level (`~/.dsh/dsgs` plus user-level
bootstrap skills). After that:

```
new working directory → new session → type /start
```

`/start` checks whether the workspace is initialised; if not it initialises it first, then walks you
through onboarding.

## A round of play

The one-shot pipeline is the shortest path from "an idea" to "a game someone can play", and it is the
part most worth watching work:

```
/prototype          → one-shot-new    prototypes/<name>/ : page, config, provenance, brief
                      [/run]          → one-shot-run     headless Chrome plays it from a fresh start
                                                          and stops where it should, with a screenshot
/check              → one-shot-check  keep pins vs config, brief checklist, evidence, a check record
/tune               → one-shot-tune   a tuned number goes back into config.js with a feel-log line
/share              → one-shot-share  dist/ without the debug panel, and it fails if any file still names it
/grow               → one-shot-grow   guard → copy → replay: a Web project at the root, compared
                                      frame by frame with the original
```

A grow session, from installing the toolchain to the final comparison, looks like this:

```
npm ci                     → added 47 packages
npm run build:single       → dist-single/index.html 4.14 kB
replay --as reference      → errors 0 · exact yes
replay --as copy           → errors 0 · match yes
replay --as story          → against reference · match yes
accept                     → accepted.tsv + accepted.png
```

`page-shot` finds Chrome, Edge, Chromium or Playwright's headless shell, gives it a profile of its own,
talks to it over the DevTools protocol with the WebSocket built into Node (nothing to install), and
writes the screenshot. When no browser exists it says so and exits 3 — it never invents a pass.

## Upgrade

Run `/update` inside an initialised workspace (0.2.1 and later):

```
/update
```

It reads the installed version and the newest release, shows the commands it will run, and runs them only after
you agree. Restart the client afterwards — the new skills appear in a new session.

**Is this workspace initialised?** Yes when `.dsh/skills/start/SKILL.md` or `.dsgs-installed.json` exists in the
project root. If neither is there, open the project in DSH, start a new session and type `/start`: that
initialises it once, and every later session in the same project can use `/update`.

**Coming from 0.2.0 or earlier?** `/update` only exists from 0.2.1 on, so the first update is manual:

```pwsh
dsh plugin --profile web remove deepseek-harness-game-studios
dsh plugin --profile web add https://github.com/HYClub/deepseek-harness-game-studios
```

Desktop app users do the same through `Plugins` (see below). Every update after that is one `/update`.

**Desktop app** — the app owns its plugin profile, so the command line cannot change it. Open `Plugins`, uninstall
`deepseek-harness-game-studios`, choose `Add plugin`, paste
`https://github.com/HYClub/deepseek-harness-game-studios`, install, then restart the app. `/update` still reports
the version and tells you when this is needed.

## What the plugin writes to your machine (and how to undo it)

| Path | What |
|---|---|
| `~/.dsh/dsgs/**` | framework payload (skills, agents, rules, hooks, scripts, engines, docs, instruction files) |
| `~/.dsh/skills/dsgs-init/SKILL.md`, `~/.dsh/skills/start/SKILL.md` | user-level bootstrap skills |

It never touches a project directory and never overwrites project files. To undo:

```pwsh
Remove-Item -Recurse -Force "$env:USERPROFILE\.dsh\dsgs"
Remove-Item -Recurse -Force "$env:USERPROFILE\.dsh\skills\dsgs-init","$env:USERPROFILE\.dsh\skills\start"
# then uninstall the plugin and restart dsh web
```

### ⚠️ Partly equivalent — works, with a stated limit

| Item | What works | What does not, and why |
|---|---|---|
| 3 hook events | mapping implemented and unit-tested | `Notification`, `PreCompact`, `PostCompact` have no DSH event source, so they are verified at mount level only (live coverage 6/9) |
| Per-agent tool allowlists | every role card **states** the boundary in its body (`工具边界 …：read, glob, grep, …`), so a delegating model reads it | DSH's `subagent` accepts no per-agent tool set and there is no agent registry, so the runtime cannot enforce it |

| Scripted play without a browser | every non-browser row is produced (keep pins, checklist, evidence, emoji, brief words) | the play itself needs Chrome, Edge, Chromium or Playwright's headless shell; without one the rows say `not_assessed` and the command exits 3 |

### ❌ No equivalent — reason and substitute

| Item | Why | Substitute |
|---|---|---|
| Docked status bar above the composer | DSH's client roster only lists `@deepseek-ai/*` packages (measured: 60+ entries, ours absent even with a `dsh.client` declaration) | `/statusline` skill + `node .dsh/statusline.mjs`; the runtime half (turns/tokens/cache/context %) is already covered by DSH's own status bar |
| Pre-action reminders on PreToolUse | `tools/pre-execute` only carries `allow/deny/cancel/ask`; `additionalContexts` is read from the final tool result; `agent.inject()` mid-execution has no effect | `validate-commit` / `validate-push` are also registered on **PostToolUse** (reminder arrives after the action); set the plugin row `advisory: deny` to block before the action |
| `!`cmd`` pre-execution lines | DSH has no pre-execution | rewritten as a "prerequisite command" block the model runs itself |

## Testing your own customizations

DSGS is a template you are meant to edit. `DSGS Skill Testing Framework/` is how you check that an
edited or newly written skill still holds up — a catalog of all skills and agents, per-category quality
rubrics, behavioral specs, and templates for writing specs of your own.

```
/skill-test static [name]     # structural linter
/skill-test category [name]   # category-specific quality rubric
/skill-test spec [name]       # behavioral spec assertions
/skill-test audit             # coverage report across skills and agents
/skill-improve [name]         # test-fix-retest loop; keeps or reverts on score change
```

It tests the *framework*, never your game — game tests live in `tests/`.
